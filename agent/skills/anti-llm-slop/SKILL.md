# Anti-LLM Slop

## 1. Code comments

Write zero comments unless they explain a non-obvious why: a workaround, a perf hack, a business decision. Never write:

- Echoes of the code below (`// Increment counter`, `// Return the result`, `// Function to calculate total`)
- Section headers in small functions (`// Initialize`, `// Process data`, `// Respond`)
- Line-by-line import summaries
- Placeholder or apologetic notes (`// TODO: implement later`, `// Note: replace with your real key`)
- Decorative borders or comment ASCII art
- Narrating control flow (`// Check if user exists`, `// Loop through items`, `// If error, throw`)
- Restating type signatures in JSDoc (`@param {string} name - The name` when the type already says it)
- Comments above one-line functions that restate the function name (`// Gets the user` above `getUser()`)
- Thanking or crediting the AI (`// Generated by Claude`, `// AI-assisted`)
- Change-log comments inline (`// Added for the new auth flow`, `// Updated to fix bug #123`)

Required comments (a11y, security, why-docs) are not slop — keep them.

## 2. Code structure

These are the most common structural tells that flag code as AI-generated. Remove on sight:

### Defensive overkill
- Try/catch wrapping code that cannot throw (pure transforms, object access on known shapes, synchronous math)
- Null checks on values that are already guaranteed by the type system or framework (`if (router) router.push(...)` inside a React component where `useRouter` never returns null)
- Validating internal function arguments that only your own code calls — validate at system boundaries (user input, API responses), trust your internals
- `typeof x !== 'undefined' && x !== null` when `x != null` does the same, or when the type already excludes nullish
- Fallback values for impossible cases (`?? 'default'` on a required field that's never missing)

### Verbose ceremony
- Creating an `interface` or `type` for a props object with 1–2 members — inline it: `({ name }: { name: string })`
- `constants.ts` with one or two constants — put them where they're used
- `types.ts` that re-exports from a single source or holds one type
- `utils.ts` / `helpers.ts` as a dumping ground — colocate the function with its only consumer
- Extracting a variable used exactly once (`const isValid = x > 0; if (isValid)` → `if (x > 0)`)
- Single-use `handleX` wrappers around one expression (`const handleClick = () => setOpen(true)` → `onClick={() => setOpen(true)}`)
- Enum-like const objects for 2–3 values that are only compared as strings — use a union type or just the literal
- `export default` plus a redundant named export of the same thing
- `async` on functions that never `await` anything
- Barrel `index.ts` files that re-export a single module — import the module directly
- Wrapping a callback in `useCallback` that is not passed as a prop or dep to a memoized child

### Over-abstraction
- A generic with one concrete instantiation (`Repository<T>` only ever used as `Repository<User>`)
- Factory, strategy, or builder patterns with a single implementation
- Config objects for values that never change and are read in one place
- Wrapper components that add no logic, only pass-through props (`<AppButton {...props} />` that renders `<button {...props} />`)
- Abstracting code "for reuse" when there is exactly one call site — inline it

### Filler structure
- Empty or near-empty files that exist "for completeness" (`services/index.ts` exporting nothing)
- Test files that test implementation details ("calls setState") instead of behavior ("renders the updated count")
- Config files with every default spelled out explicitly — only set what you're changing
- `.env.example` that duplicates `.env` verbatim with dummy values for secrets that are already documented

## 3. Writing

- Start with the content in sentence 1. No setup sentences ("Certainly!", "Below is a breakdown...", "Let's take a look at...", "Here's how you can...", "Great question!") or concluding summaries ("In summary...", "Overall...", "And that's it!"). End at the last factual point or code block.
- Replace florid adjectives with concrete specifics, exact terms, or hard numbers.
- No numbered lists for simple 2-step concepts; tables only for tabular/comparative data.
- One thing, one sentence. Don't chain three related ideas with semicolons or "additionally" — split or cut.
- Don't hedge with "might", "could potentially", "it's generally recommended" when you know the answer. State it.
- Don't restate the question back before answering ("So you want to X? Here's how to X").
- Don't bookend code blocks with "Here's the code:" before and "This code does X" after — the code is visible.

### Padding detectors

Hard ban, always filler: `delve`, `tapestry`, `testament`, `beacon`, `realm`, `multifaceted`, `game-changer`, `nestled`, `in conclusion`, `it's important to remember`, `in today's fast-paced world`, `it's worth noting`, `let me walk you through`, `overall`, `firstly`, `secondly`, `thirdly`, `in essence`, `at its core`, `at the end of the day`, `without further ado`, `as mentioned earlier`, `as we can see`, `moving forward`, `to that end`, `on that note`, `having said that`, `with that being said`.

Context-dependent — delete when padding, keep when the precise term: `leverage`, `robust`, `seamless`, `unlock`, `streamline`, `elevate`, `moreover`, `furthermore`, `vital`, `crucial`, `pivot`, `notably`, `utilize` (use "use"), `implement` (use "add" or "build" when not referring to interface implementation), `functionality` (use "feature" or name the thing), `facilitate` (use "let" or "allow"), `comprehensive` (say what's covered instead).

### Structural prose tells

- Opening a paragraph with "It's worth noting that" or "Interestingly," — delete the opener, keep the fact.
- Using "This allows us to" as a bridge between every paragraph — cut it, let the next paragraph stand.
- Inserting "Let's" as false collaboration ("Let's explore", "Let's look at") — you're writing, not touring.
- Trailing every section with "For more information, see..." — link inline or not at all.
- Qualifying obvious statements with "Arguably," or "One could say" — either say it or don't.

### The em dash problem

The em dash (`—`, Unicode U+2014) is the single most reliable typographic fingerprint of LLM-generated text. Humans writing technical content almost never reach for it. LLMs use it constantly: in appositive phrases, as a colon substitute, to inject parenthetical asides, and to glue independent clauses together. A document with five em dashes per paragraph reads as AI-written regardless of content quality.

**Default rule: do not use `—` at all.** Rewrite every instance:

| LLM pattern | Human rewrite |
| --- | --- |
| `X — a fast, modern tool — does Y` | `X (a fast, modern tool) does Y` or split into two sentences |
| `The parser handles JSON — and XML` | `The parser handles JSON and XML` |
| `This is critical — without it, builds fail` | `This is critical. Without it, builds fail.` or `This is critical because without it, builds fail.` |
| `Supports three modes — read, write, admin` | `Supports three modes: read, write, admin` |
| `Fast — but correct` | `Fast but correct` |

Acceptable **only** when all three hold: (1) the content is prose intended for human readers (blog post, long-form docs), not code/comments/commit messages/READMEs, (2) no more than one per paragraph, and (3) parentheses or a period genuinely read worse. When in doubt, use a period and start a new sentence.

The en dash (`–`) for ranges (`3–5 items`, `2020–2024`) is fine. The hyphen (`-`) for compound words is fine. The problem is specifically `—` used as a sentence-structure crutch.

## 4. Documentation / README

- Don't open with "This project is a..." — name what it does in the first line as an action: `Converts X to Y`, not `A tool for converting X to Y`.
- No "Overview" section that restates the title or first sentence.
- No "Prerequisites" section listing obvious dependencies (Node.js for a JS project, Python for a Python project) — list only non-obvious ones.
- No table of contents for documents under ~100 lines.
- No badges that don't convey real information (a static "MIT" badge when LICENSE is in the repo, a "PRs Welcome" badge on a solo project).
- Don't write API docs that restate the function signature in prose ("The `getUser` function takes a `userId` parameter of type `string` and returns a `Promise<User>`" — the types already say that). Document behavior, edge cases, side effects.
- Changelog entries must name what changed — "various improvements" or "bug fixes" are not entries.
- "Contributing" sections copy-pasted from templates belong only in projects that accept contributions and have actual contribution rules.
- No emoji bullets in technical docs (":rocket: Getting started", ":wrench: Configuration") unless the project's voice uses them.

## 5. Git messages

- No restating the obvious from the diff: `feat: add onClick handler to Button` when the diff is one line adding an onClick.
- No multi-paragraph commit bodies for one-line changes.
- No empty semantic prefixes: `refactor: improve code quality`, `chore: update files`, `fix: fix bug` — name the actual thing.
- No AI politeness in PR descriptions ("I've made the following changes", "This PR aims to") — state what changed and why.

## 6. Reviewing existing content

Given AI-generated text or code, scan in this order:

1. **Delete** filler files, empty abstractions, unused exports, barrel-only modules.
2. **Inline** single-use extractions: one-call helpers, one-field types, one-constant files.
3. **Strip** intro/conclusion buffers, padding phrases, hedge words.
4. **Unwrap** unnecessary try/catch, null guards on non-nullable paths, redundant async.
5. **Replace** vague prose with concrete specifics, exact terms, or hard numbers.
6. **Keep** anything the user asked to keep: walkthroughs, docs, educational notes, a11y, security.
